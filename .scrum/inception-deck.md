# インセプションデッキ
- status: agreed

## 1. 我々はなぜここにいるのか
- ★ システム思考に詳しくない作り手でも、気軽にシミュレーションゲームの基盤を作れるようにする。
- 因果ループ図とストック&フローの考え方で、シミュレーションゲームを設計できるようにする。
- 作ったゲームを、PC とスマホで遊べる最終製品として届けられるようにする。

## 2. エレベーターピッチ
> システム思考の専門知識がなくても、資源や人口が増えたり減ったりして動くシミュレーションゲームを作りたい個人・小規模のゲーム制作者（PO 自身を含み、他の制作者にも広げる）向けの、Meguri という Godot 用のシミュレーションゲーム基盤である。これはストック・フロー・ルールを定義するだけで、ゲームの中核の仕組みを動かして遊べる。Godot でロジックを一から書く方法とは違って、ループの暴走や停滞を確かめる検証の道具が最初から付いている。また、Machinations や Vensim とは違って、設計したモデルがそのまま PC とスマホで遊べる製品のゲームとして動く。

## 3. パッケージデザイン
- プロダクト名：Meguri（めぐり）。「巡り」から取り、資源が流れ、ループが巡って世界が回る様子を表す。
  - 2026-11-04 時点で、ゲームエンジン・シミュレーションツール・Godot アドオンの分野に同名は見つからなかった。商標と Godot Asset Library は未確認である。
- キャッチコピー：「つながりを描けば、世界が動き出す。」
- 利用者から見た価値：
  1. 理論を知らなくても、生きているような世界が作れる。「人口が増えると食料が減る」のような関係を書き並べるだけで、町や店が自分で変化し始める。
  2. 遊ぶ前に、ゲームが壊れていないと分かる。「お金が無限に増える」「すぐに全滅する」といったバランスの崩れを、テストプレイの前に見つけられる。
  3. 作ったものが、そのまま PC とスマホのゲームになる。試作から製品までを作り直さずにつなげられる。

## 4. やらないことリスト
### やる
- ストック・フロー・補助変数（計算式）・定数を扱うシミュレーションコアを作る。ターン制で一斉に更新する。
- 時間遅れと、ストックの上限・下限を扱う。
- モデル（ストック・フロー・アクション・イベント・勝敗条件）を、コードとは分けたデータとして定義できるようにする。形式は「後で決める」で検討する。
- プレイヤーのアクション、条件付きのイベント、勝利・敗北条件を扱うゲーム層を作る。
- 画面なし（ヘッドレス）で、数値と文字だけで遊べるテキスト版を作る。
- プレイヤー不在で N ターン自動で回し、推移を CSV に出す検証機能を作る。
- CSV を読んで推移をグラフにする Python スクリプトを付ける。
- サンプルゲーム「小さな町の経営」を作る。
- サンプルを Godot の最小限の画面（状態表示・アクションのボタン・推移のグラフ）で遊べるようにし、PC と Android に書き出せることを確かめる。

### やらない
- マルチプレイ、オンライン機能、3D 表示。
- 製品ゲームとしての作り込み（絵・音・演出）と、ストアでの販売。
- Vensim や XMILE 形式のモデルの読み込み。

### 後で決める
- モデルの定義形式（JSON、Godot の Resource、ビジュアルエディタで作るデータなど）。
- 因果ループ図やストック&フロー図を画面上で描くビジュアルエディタ。PO は「おそらく欲しくなる」と見ており、やらない方針ではない。
- エージェントベースのシミュレーション（住民1人ずつを個別に動かす方式）。やらない方針ではない。
- Godot Asset Library でアドオンとして配布するか。配布する場合のライセンス。
- iOS への書き出しの確認（Mac と Apple の開発者登録が必要になるため）。
- 多言語対応。

## 6. 技術的な解決策
### 技術スタック
- ゲームエンジン：Godot 4 系の最新安定版。具体的なバージョンは導入時に確認して固定する。
- 言語：GDScript。PO が Python 経験者であり、文法が近いためである。
- テスト：gdUnit4。画面のテスト（シーンランナー）を書きやすく、GitHub Actions 用の公式 Action があるためである。Godot のバージョンとの対応は導入時に確かめる。
- CI：GitHub Actions で、ヘッドレスの Godot を使ってテストを回す。
- 分析：Python（pandas、matplotlib）で、検証機能が出した CSV をグラフにする。

### 構成の概要
コアと画面は、REST API と SPA のように別プログラムには分けない。同じ Godot アプリの中で層を分け、画面はコアの関数を直接呼び、シグナルで通知を受ける。

1. シミュレーションコア：ストック・フロー・補助変数・定数・時間遅れを扱い、1ターンずつ一斉に更新する。Godot の Node に依存しない純粋なクラスで作り、画面なしでテストできるようにする。
2. ゲーム層：アクション、条件付きイベント、勝敗条件を扱う。コアの上に乗る。
3. モデルの読み込み：定義データを読み、コアとゲーム層を組み立てる。形式は後で決めるので、読み込み部分を差し替えられる形にする。
4. ヘッドレス実行：`godot --headless` で、テキスト版のプレイと、N ターンの自動実行・CSV 出力を行う。
5. 画面（UI）：Godot のシーンで、状態表示・アクションのボタン・推移のグラフを作る。コアとゲーム層を呼び出すだけにする。
6. 分析スクリプト：リポジトリ内に Python のスクリプトを置き、CSV を読んでグラフにする。

コアとゲーム層が外に公開する関数とシグナル（例：`step()`、`get_stock()`、`apply_action()`、`turn_finished`）を、層の間の API とする。

ネットワークで分けない理由は、スマホでオフラインで遊べる必要があること、計算が軽くサーバに分ける利点が無いことである。層を分ける理由は、画面なしでのテストと自動実行、画面の作り直しへの耐性、将来コアだけをアドオンとして配れることである。

### 技術的な制約
- 計算式の評価に Godot の `Expression` クラスを使う場合、式からメソッドを呼べてしまう。他の制作者が書いたモデルを読み込む想定なので、使える関数を制限する。
- ランダムなイベントは乱数のシードを固定できるようにし、検証の結果を再現できるようにする。
- C# と Rust は当面使わない。性能が足りなくなった場合に、Rust（`gdext`）を部分的に使う道は残す。
- 手元に Godot がまだ入っていない。最初のスプリントで導入する。

## 7. 夜も眠れない問題
| # | リスク | 影響 | 対策 | 兆候の見つけ方 |
|---|---|---|---|---|
| 1 | シミュレーションとしては正しく動くが、ゲームとして面白くない | エンジンの価値を示せない | 早いスプリントでサンプルを遊べる状態にし、毎スプリントのデモで PO が遊ぶ | デモで PO が「もう1ターン遊びたい」と感じない |
| 2 | 「システム思考に詳しくなくても気軽に作れる」が実現できない | 1問目の★を満たせない | 定義形式を決める前に、PO が実際にサンプルのモデルを書いてみて、つまずく点を集める | PO がサンプルのモデルを自力で書き換えられない |
| 3 | ビジュアルエディタやエージェントベースに手を広げ、範囲が膨らむ | 最初のリリースが遠のく | 「後で決める」の項目は、スプリント計画で明示的に判断してから着手する | スプリントゴールを2回続けて達成できない |
| 4 | Agent が書いた GDScript を PO が読めず、判断できない | レビューで受け入れ判定ができなくなる | デモと台本で動きを見せる。コードの要点を日本語で説明する | PO がレビューで「何が変わったか分からない」と感じる |
| 5 | Godot や gdUnit4 の更新で動かなくなる | 開発が止まる | バージョンを固定し、更新は PBI として計画して行う | 更新後に CI が失敗する |
| 6 | スマホで動かない、または画面が使いにくい | PC・スマホで遊ばせるという目標を満たせない | 早い段階で Android への書き出しと実機での操作を確かめる | 書き出しに失敗する。小さい画面でボタンが押しにくい |
| 7 | 他の制作者が書いたモデルファイルから、計算式経由で任意の処理が実行される | 利用者の環境が危険にさらされる | 式で使える関数を許可リストで制限し、security-review 枠で確認する | レビューで制限の抜けが指摘される |
| 8 | Agent の利用費が想定を超える | 継続できなくなる | capacity を守り、スプリントごとに費用を確認する | 1スプリントあたりの費用が増え続ける |
| 9 | PO が1人のため、時間が取れずに止まる | 開発が長期間止まる | 1スプリントを小さく保ち、いつでも中断・再開できるようにする | 前回のスプリントから間が空く |

- 最も重いリスクは1と2である。

## 8. 期間を見極める
- 最初のリリース（v0.1）：2027年1月末を目安とする。外部から決まった期限は無い。
- v0.1 の最小範囲：「小さな町の経営」を、Godot の画面で PC と Android で遊べる。同じモデルを、画面なしで自動実行して CSV とグラフで検証できる。
- 1スプリントは、PO の都合に合わせて1〜2週間に1回程度回す想定である。

| 節目 | 目安 | 範囲 |
|---|---|---|
| M1：動くコア | スプリント 1〜2（2026年11月中） | Godot と gdUnit4 の導入、CI、シミュレーションコア、画面なしのテキスト版で町が数ターン動く |
| M2：遊べて検証できる | スプリント 3〜4（2026年12月中） | アクション・イベント・勝敗条件、N ターンの自動実行と CSV 出力、Python のグラフ化。PO がサンプルのモデルを書いてみて、定義形式とビジュアルエディタの扱いを決める |
| M3：画面とスマホ | スプリント 5〜6（2027年1月中） | 状態表示・アクションのボタン・推移のグラフの画面、PC と Android への書き出し |

## 9. トレードオフスライダー
| 順位 | 軸 | 理由 |
|---|---|---|
| 1 | 使いやすさ（気軽さ） | 「システム思考に詳しくなくても気軽に作れる」が、このプロジェクトの最も重要な存在理由だからである。 |
| 2 | 品質 | エンジンは他の制作者のゲームの土台になり、不具合や安全性の問題がそのまま利用者に波及するからである。 |
| 3 | 予算 | 個人のプロジェクトで、Agent の利用費は PO の負担になるからである。 |
| 4 | 時間 | 外部から決まった期限が無く、v0.1 の時期は目安だからである。 |
| 5 | スコープ | 範囲は、優先度の低い機能から削っても、上位の軸を守れるからである。 |

- 期限が迫った場合は、まず範囲を削り（例：推移のグラフ画面を外し、CSV と Python のグラフだけにする）、それでも足りなければリリースの時期を延ばす。テストやレビューの省略と、分かりにくい作りのままの公開はしない。

## 10. 何がどれだけ必要か
- 期間：v0.1 まで約3か月（2026年11月〜2027年1月末）、6スプリント程度。
- 費用：
  - Agent の利用費は、契約中の Claude のプランの範囲内で回し、追加の従量課金は使わない。プランの利用上限に当たった場合は、そのスプリントを中断し、上限が戻ってから再開する。
  - Godot、gdUnit4、Python のライブラリは無料である。GitHub は public リポジトリなので、Actions も無料枠で足りる想定である。
  - Google Play の開発者登録と Apple Developer Program の費用は、ストアに出すと決めたときに判断する。v0.1 では不要である。
- チーム編成：
  - PO：1名（ユーザ）。
  - implement 枠：Godot と GDScript の実装。
  - design 枠：画面の UI 仕様。
  - code-review 枠：コードレビュー。
  - security-review 枠：セキュリティレビュー。特に計算式の評価の制限（7のリスク7）を見る。
  - extra-review 枠：ゲームデザインとバランスの観点のレビュー（7のリスク1への対策）。
  - 具体的な Agent は、チーム編成でカタログから選び、PO の承認を得る。
  - 人間の関係者は現時点では不要である。サンプルが遊べる状態になったら、テストプレイヤーを探すかを判断する。
- 費用の上限を超えそうなときは PO が判断する。スクラムマスターは、兆候をスプリントの途中で PO に伝える。
