# チーム合意

### T2-1: 外部入力と数値の不変条件を、経路の表と判定基準つきで守る（T1-1 を置き換える）
- なぜ（根本原因）:
  - T1-1 は「入口の例」で書かれ、次の3点を共通の基準として定めていなかった。
    - 検査する範囲（定義時だけか、実行時の計算結果や人が打つ入力も含むか）
    - 不可視文字の判定対象の集合（「など」付きの例示だった）
    - テストの網羅の基準（「1件以上」だけだった）
  - そのため、実装者とレビュアーがそれぞれの解釈で判断した。
  - スプリント2では、step の加算による非有限、不可視文字の判定の抜け（2つの PBI で重複）、標準入力の行の長さが、should として残った。
- 誰が: implement 枠（実装時）。code-review 枠・security-review 枠・extra-review 枠（判定時）
- いつ: 値を受け取る、計算する、または出力するコードを書くとき、あるいはそのコードをレビューするとき
- どこで: src/ のすべてのコード、そのテスト、実装の報告の assumptions
- 何を: 次の不変条件を守る。
  1. **有限性**：ストック・定数・式の途中値・計算結果は、常に有限である。NaN・無限大が生じた時点で、Error で止める。止まるのは、定義時なら定義、パース時なら構文、実行時ならそのターンであり、状態は変えない。
  2. **失敗の返し方**：失敗は `Error` コードと `last_error` で返す。NAN などの値では返さない。`last_error` は、成功したときに空にする。
  3. **上限**：外部由来の値には、長さ・個数・深さの上限を置く。外部由来とは、次のすべてを指す。
     - モデルの定義
     - 式
     - 標準入力
     - コマンドライン引数
     - ファイル
     - 人が打つ入力を1行読むときも、上限を超えた分は、切り詰めるか Error にする。
     - 空白だけの名前と、不可視文字だけの名前は、空の名前として扱う。
  4. **出力のエスケープ**：利用者由来の文字列を、ログ・エラー文・画面に出すときは、エスケープする。
     - 対象の文字は、Unicode の一般カテゴリで定める。対象は Cc・Cf・Zl・Zp・Co、U+0020 以外の Zs、Default_Ignorable_Code_Point である（Default_Ignorable_Code_Point は、Sprint 3 のリファインメントで PO が加えた）。
     - 判定には、コードポイントの範囲表を使う。範囲表は共通の関数（ModelCheck）の1か所に置く。一覧の列挙で判定してはならない。
- どうやって:
  - implement は、報告の assumptions に「経路の表」を書く。表の作り方は、T4-2 に従う。
  - 外部由来の値を受け取る公開関数には、敵対的な値の共有一覧を全件流すテストを置く。
    - 共有一覧は、`test/` の1か所に置く。
    - 一覧の中身は、NaN・INF・-INF、1e308+1e308 になる組、`""`、`" "`、U+200B だけ、U+202E を含む文字列、長さ10万の文字列、深さ1000の入れ子である。
    - 新しい種類の値は、一覧に足すだけで、全関数のテストに効くようにする。
  - escape のテストは、範囲表のすべての範囲を回し、そのまま出力された文字があれば失敗とする。
  - レビュアーは、次の2つを must とする。
    - 経路の表に空欄がある。
    - 表にある経路で、1〜4に反する実装がある。
- 効果の確認: スプリント3のレビューで、1〜4に当たる新規の指摘（既知の should の再報告は除く）が、should も含めて0件であれば、効果ありとする。あわせて、同じ種類の指摘を2つ以上の枠が重ねていないことも条件とする。
- 行き先: チーム合意

### T1-2: should の指摘に行き先を付け、重なったものを後続 PBI に流す
- なぜ（根本原因）: should はマージを止めないので、誰も引き取らない。また、判定書式にも記録にも、行き先を書く場所が無い。スプリント1では34件の should が行き先を持たずに残り、同じ種類の指摘が PBI をまたいで繰り返された。
- 誰が: code-review 枠・security-review 枠・extra-review 枠（指摘時）、スクラムマスター（集約時）
- いつ: 各 PBI のレビューで should を出すとき。および、スプリントの実行フェーズを終えて `phase` を `demo` にする直前
- どこで: レビューの findings、スプリントファイルの「記録」、バックログの PBI のコメント
- 何を:
  - レビュアーは、should の各行の末尾に「→ 行き先」を1つ書く。行き先は `#<PBI番号> の受け入れ基準`、`新規改善 PBI`、`対応不要（理由）` のどれかとする。
  - スクラムマスターは、should を集約表（指摘・枠・行き先）にまとめる。
- どうやって:
  - スクラムマスターは、レビューの依頼に「should には → 行き先を付ける」と書く。
  - 次の2種類の should は、スクラムマスターが行き先の PBI に、受け入れ基準の追記案としてコメントする（`review: Sprint <N>` と書く）。
    - 2つ以上の枠が重ねて出したもの
    - security-review が出したもの
  - 行き先の PBI が実装中であれば、その担当にも伝える。
  - 追記するかどうかは、次のリファインメントで PO が決める。
- 効果の確認: 行き先が書かれた should が90%以上あり、重なった should がすべて PBI にコメントされていれば、効果ありとする（スプリント2：100%、効果あり）。
- 行き先: チーム合意

### T2-2: 持ち越した should を、計画で採否を決め、レビューに既知として渡す（T1-2 を補う）
- なぜ（根本原因）:
  - T1-2 は、should を後続の PBI に回すだけで、行き先で実装される保証が無かった。
  - 後続のレビュアーには、既に行き先が付いた should が渡らない。
  - その結果、不可視文字の判定の抜けが、#16 と #10 で別々の指摘として再報告され、二重に数えられた。
  - 「PO の判断待ち」のまま実装に入ったので、#10 の実装者は対応しなかった。
- 誰が: スクラムマスター（一覧の作成と、計画・レビューの依頼への添付）、PO（採否）、各レビュー枠（再報告の扱い）
- いつ: スプリント計画のとき。および、持ち越した should の対象になるコードを含む PBI のレビュー依頼を出すとき
- どこで: スプリント計画で PO に示す資料、レビューの依頼、スプリントファイルの「記録」
- 何を:
  1. スクラムマスターは、スプリント計画で「持ち越した should の一覧」（指摘・元の PBI・行き先の PBI）を示す。行き先がそのスプリントの PBI である should については、受け入れ基準に入れるかどうかを PO に決めてもらい、記録する。「PO の判断待ち」のまま実装に入らない。
  2. スクラムマスターは、レビューの依頼に「既知の should」の節を設けて一覧を貼る。レビュアーは、既知の should と同じ指摘を新規として数えない。findings の末尾に「既知: #<元の PBI>」と1行で書く。
  3. security の should のうち、行き先の PBI で採用されたのに、別の PBI で同じ種類の欠陥が再び見つかったものは、must とする。
- どうやって: スクラムマスターは、前の PBI のレビュー記録から、行き先が後続の PBI か新規改善 PBI である should を抜き出し、計画の資料とレビューの依頼に貼る。集計では、should を「新規」「既知」「対応不要」に分けて数え、metrics.md にも分けて記録する。
- 効果の確認: スプリント3で次の2つを満たせば、効果ありとする。
  - 行き先がスプリント3の PBI である持ち越した should の採否が、計画時に100%決まっていた。
  - 既知の should が新規として再報告された件数が0件だった。
- 行き先: チーム合意

### T4-2: 経路の表に「組み合わせ」と「処理量」を足し、共通部品は契約ごとに確かめる（T3-2 を置き換える）
- なぜ（根本原因）:
  - T3-2 は Sprint 4 で「効果なし」だった。表は全 PBI で空欄なしだったが、不変条件に当たる新規の指摘が2件出た。
    - #29：escape_reason が、エスケープ済みの文を表記の途中で切る。
    - #35：判定のたびに条件を組み立て直し、条件990個で1ターン約3.2秒かかる。
  - 分析し直すと、T3-2 の前提が誤っていた。表は「経路ごとに値の形が守られるか」だけを問う。欠陥は、経路の途中の共通部品の契約（切るのはエスケープの境界）と、規模に比例する処理量にあった。不変条件1〜4にも、表の6列にも、この2つが無い。
- 誰が: implement 枠（表を埋め、組み合わせのテストと規模の測定を置く）。各レビュー枠（表と実コードを突き合わせる）。security-review 枠（列7の規模を実際に流す）
- いつ: 値を受け取る、計算する、または出力するコードを書く PBI の、実装の報告のとき。および、そのレビューのとき
- どこで: 実装の報告の assumptions の「経路の表」の節。test/ の共通部品のテスト。test/support/hostile_values.gd
- 何を:
  1. 経路の表は、行と列で作る。
     - 行は「入口 → 出口」の組である。
       - 入口：モデルの定義、式、標準入力、コマンドライン引数、ファイル、アクションの入力、計算結果。
       - 出口：エラー文（last_error）、ログ、標準出力・画面、ファイル、保存される状態。
     - 列は次の7つである。
       - 1〜4：T2-1 の不変条件1〜4。
       - 5：生のバイト列（不正な UTF-8、NUL、CR）。
       - 6：出力の長さと組み合わせの正しさ。エスケープで伸びた後の長さに上限があり、上限で切った出力が、エスケープの表記の途中や文字の途中で終わらないこと。
       - 7：処理量。ターン数や要素数に比例して増える処理について、想定する最大の規模（例：条件1000個、100ターン）と、その規模での実測時間を書く。
     - その PBI が触らない入口や出口は、「該当なし」と理由を書く。空欄は残さない。
     - 外から入る境界（標準入力、ファイルなど）の行には、実際のプロセスかバイト列の供給元を通すテストの名前を書く。
  2. 共通部品（escape、切り詰めなど）を変える、または新しく使う PBI では、部品の組み合わせ（例：escape × 長さの上限）のテストを置く。
  3. 列7の測定は、テストか demo のスクリプトで再現できる形で残す。
- どうやって:
  - レビュアーは、次の3つを must とする。
    - 表の空欄。ただし、must を出す前に、implement の報告の元の表を読んで空欄を確かめる（T4-3）。
    - 該当なしの理由が誤っていること。
    - 表にある経路で、列1〜7に反する実装。
  - security-review は、列7に書かれた規模を実際に流し、実測時間を確かめる。
- 効果の確認: Sprint 5 のレビューで、次の2つを満たせば効果ありとする。
  - 列1〜7に当たる新規の指摘（既知を除く）が、should も含めて0件である。
  - 処理量を持つ PBI のすべてで、列7に規模と実測時間が書かれている。
- 行き先: チーム合意

### T3-3: 同時に走らせる Agent を3つまでにし、実装は受け入れ基準ごとにコミットする
- なぜ（根本原因）: Sprint 3 では、レビュー6つと実装1つ（合わせて7つ）を同時に走らせていた。そのため、利用上限で止めたときに失う作業が大きかった。レビュー6つはやり直しになり、#24 の実装はコミットしていない変更のまま止まった。同時に走らせる数の上限も、途中で保存する決まりも無かった。
- 誰が: スクラムマスター（起動の数）。implement 枠（途中のコミット）
- いつ: スプリントの実行中に、Agent を起動するたび。および、実装の途中
- どこで: スプリントファイルの実行計画、Agent の起動、実装の作業ディレクトリ
- 何を:
  1. スクラムマスターは、同時に走らせる Agent を3つまでにする。1つの PBI の3つのレビューを先に終えてから、次の PBI のレビューを起動する。実装とレビューを並べるときも、合わせて3つまでとする。
  2. implement は、受け入れ基準を1つ満たすごとにコミットする。コミットのメッセージには、満たした基準を書く。中断しても、git log から続きを追えるようにする。
- どうやって:
  - スクラムマスターは、実行計画に「同時に走らせる数：3」と書く。起動の前に、走っている数を数える。
  - implement の依頼に「受け入れ基準ごとにコミットする」と書く。
- 効果の確認: Sprint 4 で次の2つを満たせば、効果ありとする。
  - 中断した場合に、やり直した Agent の起動が1回以下である。
  - 中断した実装の作業ディレクトリに、コミットしていない変更が受け入れ基準1つ分以下しか残っていない。
  - 中断が起きなかった場合は「判定不能」とし、同時に走らせた数の最大値を記録する。
  - Sprint 4：中断が無く「判定不能」。同時に走らせた数は最大3だった。#35 は基準2〜6を1つのコミットにまとめた。Sprint 5 も同じ条件で判定する。
- 行き先: チーム合意

### T4-1: Issue の本文を決まったコマンドで読み、「全」「すべて」の基準は対象を列挙してテストと1対1で突き合わせる
- なぜ（根本原因）: Sprint 4 の差し戻し1回（#29）は、受け入れ基準「全公開関数」のテストの漏れだった。原因は2つある。
  - 依頼とプロトコルに、本文を取得するコマンドが決まっていなかった。#29 の implement は `gh issue view --comments` を使って本文を見られず、見えないことを「情報が無い」と受け取って作り始めた。
  - 「全 X」の基準を、対象を列挙して数える手順が無かった。implement は対象を「式を受け取る関数」と狭く解釈し、レビューも表の行とテストの対応を照合しなかった。
- 誰が: スクラムマスター（依頼の書式）。implement 枠（列挙表を作る）。code-review 枠（列挙表を照合する）
- いつ: implement の依頼を出すとき。受け入れ基準に「全」「すべて」「各」を含む PBI の実装の報告とレビューのとき
- どこで: implement の依頼の先頭。実装の報告の「列挙表」の節。code-review の判定
- 何を:
  1. スクラムマスターは、implement の依頼の先頭に「最初に `gh issue view <番号> --json title,body,comments` で本文を読む。本文が取れなければ、作り始めずに blocked で報告する」と書く。
  2. implement は、受け入れ基準に「全」「すべて」「各」を含むとき、対象を grep などで機械的に列挙し、対象ごとにテスト名を並べた列挙表を報告に付ける。列挙に使ったコマンドも書く。
  3. code-review は、列挙のコマンドを自分でも実行し、列挙表の行数と一致するか、テスト名の空欄が無いかを確かめる。不一致と空欄は must とする。
- どうやって: 列挙表の書式は「| 対象 | テスト名 |」の2列とし、表の上に列挙のコマンドと件数を書く。
- 効果の確認: Sprint 5 で次の2つを満たせば効果ありとする。
  - 本文の読み落としによる作り直しが0回である。
  - 「全」の基準の漏れによる must が0件である。
- 行き先: チーム合意

### T4-3: レビューの依頼は原文を参照させ、再レビューは差分と must に絞り、extra-review は起動する条件を決める
- なぜ（根本原因）: レビューの依頼に何を入れ、どの範囲を見せるかの規則が無い。そのため、次の3つが起きた。
  - スクラムマスターが経路の表を要約して写し、空欄ができて、security が誤った must を出した。再判定に204秒・約4.9万 tokens かかった。
  - 再レビューを初回と同じ範囲で依頼し、code-review の再判定が初回と同じ約6.4万 tokens かかった。
  - extra-review を、計算に触れない PBI（#29 のエラー文の整形）にも一律に起動した。
  - 1pt あたりの tokens は 72k（S2）→ 112k 以上（S3）→ 118k（S4、振り返りを除く）と増え続けている（デッキのリスク8）。
- 誰が: スクラムマスター（依頼の作成、起動の判断）。各レビュー枠（原文の確認、再レビューの範囲）
- いつ: レビューと再レビューの依頼を出すとき。スプリント計画で実行計画を作るとき
- どこで: レビューの依頼。スプリントファイルの実行計画
- 何を:
  1. スクラムマスターは、implement の報告の表や一覧を依頼に写さない。報告を保存したファイルの絶対パスと、節の名前を示し、レビュアーに直接読ませる。報告の全文はスプリントファイルの「記録」にも残す。
  2. 再レビューの依頼には、前回の must の一覧、手直しのコミットの範囲（`git diff <前回の承認対象>..HEAD`）、前回の判定のファイルの場所だけを渡す。レビュアーは、must の解消と手直しの差分だけを判定し、前回 approve した部分を読み直さない。
  3. extra-review は、次のどれかに当てはまる PBI だけ起動する。当てはまらない PBI は、ゴールデン値のテストの通過で代える。
     - 計算式・数値・乱数・CSV などの出力形式を変える。
     - 判定や順序（優先・時点）を変える。
     - ゴールデン値のファイルを変える。
- どうやって: 実行計画に、PBI ごとに「extra: 要／不要（理由）」を1行書く。再レビューの依頼には「再レビュー：範囲は must と差分だけ」と1行目に書く。
- 効果の確認: Sprint 5 で次の3つを満たせば効果ありとする。
  - 転記の誤りによる must と、それによる再判定が0回である。
  - 再レビューの1回あたりの tokens が、同じ PBI の初回のレビューの半分以下である。
  - 1pt あたりの tokens（振り返りを除く）が、Sprint 4 の 117,815 を下回る。
- 行き先: チーム合意
