# チーム合意

### T2-1: 外部入力と数値の不変条件を、経路の表と判定基準つきで守る（T1-1 を置き換える）
- なぜ（根本原因）:
  - T1-1 は「入口の例」で書かれ、次の3点を共通の基準として定めていなかった。
    - 検査する範囲（定義時だけか、実行時の計算結果や人が打つ入力も含むか）
    - 不可視文字の判定対象の集合（「など」付きの例示だった）
    - テストの網羅の基準（「1件以上」だけだった）
  - そのため、実装者とレビュアーがそれぞれの解釈で判断した。
  - スプリント2では、step の加算による非有限、不可視文字の判定の抜け（2つの PBI で重複）、標準入力の行の長さが、should として残った。
- 誰が: implement 枠（実装時）。code-review 枠・security-review 枠・extra-review 枠（判定時）
- いつ: 値を受け取る、計算する、または出力するコードを書くとき、あるいはそのコードをレビューするとき
- どこで: src/ のすべてのコード、そのテスト、実装の報告の assumptions
- 何を: 次の不変条件を守る。
  1. **有限性**：ストック・定数・式の途中値・計算結果は、常に有限である。NaN・無限大が生じた時点で、Error で止める。止まるのは、定義時なら定義、パース時なら構文、実行時ならそのターンであり、状態は変えない。
  2. **失敗の返し方**：失敗は `Error` コードと `last_error` で返す。NAN などの値では返さない。`last_error` は、成功したときに空にする。
  3. **上限**：外部由来の値には、長さ・個数・深さの上限を置く。外部由来とは、次のすべてを指す。
     - モデルの定義
     - 式
     - 標準入力
     - コマンドライン引数
     - ファイル
     - 人が打つ入力を1行読むときも、上限を超えた分は、切り詰めるか Error にする。
     - 空白だけの名前と、不可視文字だけの名前は、空の名前として扱う。
  4. **出力のエスケープ**：利用者由来の文字列を、ログ・エラー文・画面に出すときは、エスケープする。
     - 対象の文字は、Unicode の一般カテゴリで定める。対象は Cc・Cf・Zl・Zp・Co、U+0020 以外の Zs、Default_Ignorable_Code_Point である（Default_Ignorable_Code_Point は、Sprint 3 のリファインメントで PO が加えた）。
     - 判定には、コードポイントの範囲表を使う。範囲表は共通の関数（ModelCheck）の1か所に置く。一覧の列挙で判定してはならない。
- どうやって:
  - implement は、報告の assumptions に「経路の表」を書く。表の作り方は、T6-1 に従う。
  - 外部由来の値を受け取る公開関数には、敵対的な値の共有一覧を全件流すテストを置く。
    - 共有一覧は、`test/` の1か所に置く。
    - 一覧の中身は、NaN・INF・-INF、1e308+1e308 になる組、`""`、`" "`、U+200B だけ、U+202E を含む文字列、長さ10万の文字列、深さ1000の入れ子である。
    - 新しい種類の値は、一覧に足すだけで、全関数のテストに効くようにする。
  - escape のテストは、範囲表のすべての範囲を回し、そのまま出力された文字があれば失敗とする。
  - レビュアーは、次の2つを must とする。
    - 経路の表に空欄がある。
    - 表にある経路で、1〜4に反する実装がある。
- 効果の確認: スプリント3のレビューで、1〜4に当たる新規の指摘（既知の should の再報告は除く）が、should も含めて0件であれば、効果ありとする。あわせて、同じ種類の指摘を2つ以上の枠が重ねていないことも条件とする。
- 行き先: チーム合意

### T1-2: should の指摘に行き先を付け、重なったものを後続 PBI に流す
- なぜ（根本原因）: should はマージを止めないので、誰も引き取らない。また、判定書式にも記録にも、行き先を書く場所が無い。スプリント1では34件の should が行き先を持たずに残り、同じ種類の指摘が PBI をまたいで繰り返された。
- 誰が: code-review 枠・security-review 枠・extra-review 枠（指摘時）、スクラムマスター（集約時）
- いつ: 各 PBI のレビューで should を出すとき。および、スプリントの実行フェーズを終えて `phase` を `demo` にする直前
- どこで: レビューの findings、スプリントファイルの「記録」、バックログの PBI のコメント
- 何を:
  - レビュアーは、should の各行の末尾に「→ 行き先」を1つ書く。行き先は `#<PBI番号> の受け入れ基準`、`新規改善 PBI`、`対応不要（理由）` のどれかとする。
  - スクラムマスターは、should を集約表（指摘・枠・行き先）にまとめる。
- どうやって:
  - スクラムマスターは、レビューの依頼に「should には → 行き先を付ける」と書く。
  - 次の2種類の should は、スクラムマスターが行き先の PBI に、受け入れ基準の追記案としてコメントする（`review: Sprint <N>` と書く）。
    - 2つ以上の枠が重ねて出したもの
    - security-review が出したもの
  - 行き先の PBI が実装中であれば、その担当にも伝える。
  - 追記するかどうかは、次のリファインメントで PO が決める。
- 効果の確認: 行き先が書かれた should が90%以上あり、重なった should がすべて PBI にコメントされていれば、効果ありとする（スプリント2：100%、効果あり）。
- 行き先: チーム合意

### T2-2: 持ち越した should を、計画で採否を決め、レビューに既知として渡す（T1-2 を補う）
- なぜ（根本原因）:
  - T1-2 は、should を後続の PBI に回すだけで、行き先で実装される保証が無かった。
  - 後続のレビュアーには、既に行き先が付いた should が渡らない。
  - その結果、不可視文字の判定の抜けが、#16 と #10 で別々の指摘として再報告され、二重に数えられた。
  - 「PO の判断待ち」のまま実装に入ったので、#10 の実装者は対応しなかった。
- 誰が: スクラムマスター（一覧の作成と、計画・レビューの依頼への添付）、PO（採否）、各レビュー枠（再報告の扱い）
- いつ: スプリント計画のとき。および、持ち越した should の対象になるコードを含む PBI のレビュー依頼を出すとき
- どこで: スプリント計画で PO に示す資料、レビューの依頼、スプリントファイルの「記録」
- 何を:
  1. スクラムマスターは、スプリント計画で「持ち越した should の一覧」（指摘・元の PBI・行き先の PBI）を示す。行き先がそのスプリントの PBI である should については、受け入れ基準に入れるかどうかを PO に決めてもらい、記録する。「PO の判断待ち」のまま実装に入らない。
  2. スクラムマスターは、レビューの依頼に「既知の should」の節を設けて一覧を貼る。レビュアーは、既知の should と同じ指摘を新規として数えない。findings の末尾に「既知: #<元の PBI>」と1行で書く。
  3. security の should のうち、行き先の PBI で採用されたのに、別の PBI で同じ種類の欠陥が再び見つかったものは、must とする。
- どうやって: スクラムマスターは、前の PBI のレビュー記録から、行き先が後続の PBI か新規改善 PBI である should を抜き出し、計画の資料とレビューの依頼に貼る。集計では、should を「新規」「既知」「対応不要」に分けて数え、metrics.md にも分けて記録する。
- 効果の確認: スプリント3で次の2つを満たせば、効果ありとする。
  - 行き先がスプリント3の PBI である持ち越した should の採否が、計画時に100%決まっていた。
  - 既知の should が新規として再報告された件数が0件だった。
- 行き先: チーム合意

### T6-1: 経路の表を1か所の定義で作り、列7は資源ごとに「定義のとき」と「実行のとき」を分けて測る（T5-1 を置き換える）
- なぜ（根本原因）:
  - T5-1 は Sprint 6 で「効果なし」だった。#45 で、implement が「アクションの式は1回の評価が有界だから既存の上限で足りる」と結論し、security が保存量（1件あたり約63MB、外挿で約60GB）と定義時間（約0.66秒）の must を出した。
  - 分析し直すと、T5-1 の3軸（個数・1個あたりの大きさ・参照の広がり）は、過去の指摘（評価の時間）から帰納した軸で、評価の時間の積しか問わなかった。定義のときに保存される量と定義の時間、上限が付く単位（1回の評価か、モデル全体か）を問う欄が無かった。軸を足すだけでは、別の資源で同じ漏れが起きる。
  - 「足りるか」という是非の問いは、測らずに論理で答えられた。「上限なし」を一律 should とする規則なので、code-review も積を自分で計算しなかった。
  - さらに、表の列の定義が T2-1・置き換え済みの T4-2・T5-1 の括弧に散っていた。スクラムマスターが依頼に「T5-1」と名前だけを書き、#39 の implement は列を独自に解釈した（表の作り直しに 32,125 tokens）。
- 誰が: implement 枠（表を埋め、測る）。code-review 枠（空欄と積を確かめる）。security-review 枠（最悪の形を流す）。スクラムマスター（依頼にこの節の場所を渡す）
- いつ: 値を受け取る・計算する・出力する・定義時に保存するコードを書く PBI の、実装の報告とレビューのとき
- どこで: 実装の報告の「経路の表」と「列7の規模と実測」の節。依頼の共通ファイル
- 何を:
  1. 経路の表の定義はこの節だけに置く。依頼には「agreements.md の T6-1」と節の場所を書き、名前だけを渡さない。
     - 行は「入口 → 出口」の組である。入口：モデルの定義、式、標準入力、コマンドライン引数、ファイル、アクションの入力、計算結果。出口：エラー文（last_error）、ログ、標準出力・画面、ファイル、保存される状態。
     - 列は次の7つである。
       1. 有限性（T2-1 の1）
       2. 失敗の返し方（T2-1 の2）
       3. 上限（T2-1 の3。外部由来の値の長さ・個数・深さ）
       4. 出力のエスケープ（T2-1 の4）
       5. 生のバイト列（不正な UTF-8、NUL、CR）
       6. 出力の長さと組み合わせの正しさ（エスケープで伸びた後の長さの上限と、上限で切った出力が表記の途中で終わらないこと）
       7. 処理量（下の2）
     - 触らない入口・出口・列は「該当なし」と理由を書く。空欄を残さない。定義が見つからないときは、仮定を置かずに「定義なし」と書いて報告する。
     - 共通部品（escape、切り詰めなど）を変える、または新しく使う PBI では、組み合わせのテストを置く。
  2. 列7は「列7の規模と実測」の節に、次の表で書く。
     - 3つの軸（個数・1個あたりの大きさ・参照の広がり）の上限と、その積から導いた最悪の形を1つ以上書く。
     - 最悪の形ごとに、4つの資源を測る：定義のときの時間、定義の後に保存される量（メモリ）、1回の実行の時間、実行の後に残る量。
     - 資源ごとに、上限が付く単位（1回か、モデル全体か）を書く。モデル全体で上限が付かない資源は「上限なし」と書き、1個あたりの量 × 定義できる個数の見積りを添え、implement 自身が should として報告する。
     - 「足りる」「有界」と書く行には、最悪の形の実測値を必ず添える。実測の無い「足りる」は空欄と同じに扱う。
     - 測定はテストか demo のスクリプトで再現できる形で残す（T6-2）。
- どうやって:
  - レビュアーは、次を must とする。表の空欄、「該当なし」の理由の誤り、表にある経路で列1〜6に反する実装、処理量のある PBI で列7の資源の欄が空、実測の無い「足りる」。
  - code-review は、「上限なし」の行ごとに見積りの積を自分で計算し、判定欄に残す。見積りが DoD の天井（DoD 変更案。PO が決めるまでは、定義時間10秒・静的メモリ1GB を目安にする）を超えるなら、自己申告していても must とする。
  - security-review は、導いた最悪の形より大きくなる軸と資源が漏れていないかを確かめ、最悪の形を実際に流す。
- 効果の確認: Sprint 7 で、次の2つを満たせば効果ありとする。
  - 列7に当たる新規の指摘のうち、implement が自分で報告していなかったものが0件である。
  - 経路の表の作り直しが0回である。
- 行き先: チーム合意

### T4-1: Issue の本文を決まったコマンドで読み、「全」「すべて」の基準は対象を列挙してテストと1対1で突き合わせる
- なぜ（根本原因）: Sprint 4 の差し戻し1回（#29）は、受け入れ基準「全公開関数」のテストの漏れだった。原因は2つある。
  - 依頼とプロトコルに、本文を取得するコマンドが決まっていなかった。#29 の implement は `gh issue view --comments` を使って本文を見られず、見えないことを「情報が無い」と受け取って作り始めた。
  - 「全 X」の基準を、対象を列挙して数える手順が無かった。implement は対象を「式を受け取る関数」と狭く解釈し、レビューも表の行とテストの対応を照合しなかった。
- 誰が: スクラムマスター（依頼の書式）。implement 枠（列挙表を作る）。code-review 枠（列挙表を照合する）
- いつ: implement の依頼を出すとき。受け入れ基準に「全」「すべて」「各」を含む PBI の実装の報告とレビューのとき
- どこで: implement の依頼の先頭。実装の報告の「列挙表」の節。code-review の判定
- 何を:
  1. スクラムマスターは、implement の依頼の先頭に「最初に `gh issue view <番号> --json title,body,comments` で本文を読む。本文が取れなければ、作り始めずに blocked で報告する」と書く。
  2. implement は、受け入れ基準に「全」「すべて」「各」を含むとき、対象を grep などで機械的に列挙し、対象ごとにテスト名を並べた列挙表を報告に付ける。列挙に使ったコマンドも書く。
  3. code-review は、列挙のコマンドを自分でも実行し、列挙表の行数と一致するか、テスト名の空欄が無いかを確かめる。不一致と空欄は must とする。
- どうやって: 列挙表の書式は「| 対象 | テスト名 |」の2列とし、表の上に列挙のコマンドと件数を書く。
- 効果の確認: Sprint 5 で次の2つを満たせば効果ありとする。
  - 本文の読み落としによる作り直しが0回である。
  - 「全」の基準の漏れによる must が0件である。
- 行き先: チーム合意

### T4-3: レビューの依頼は原文を参照させ、再レビューは差分と must に絞り、extra-review は起動する条件を決める
- なぜ（根本原因）: レビューの依頼に何を入れ、どの範囲を見せるかの規則が無い。そのため、次の3つが起きた。
  - スクラムマスターが経路の表を要約して写し、空欄ができて、security が誤った must を出した。再判定に204秒・約4.9万 tokens かかった。
  - 再レビューを初回と同じ範囲で依頼し、code-review の再判定が初回と同じ約6.4万 tokens かかった。
  - extra-review を、計算に触れない PBI（#29 のエラー文の整形）にも一律に起動した。
  - 1pt あたりの tokens は 72k（S2）→ 112k 以上（S3）→ 118k（S4、振り返りを除く）と増え続けている（デッキのリスク8）。
- 誰が: スクラムマスター（依頼の作成、起動の判断）。各レビュー枠（原文の確認、再レビューの範囲）
- いつ: レビューと再レビューの依頼を出すとき。スプリント計画で実行計画を作るとき
- どこで: レビューの依頼。スプリントファイルの実行計画
- 何を:
  1. スクラムマスターは、implement の報告の表や一覧を依頼に写さない。報告を保存したファイルの絶対パスと、節の名前を示し、レビュアーに直接読ませる。報告の全文はスプリントファイルの「記録」にも残す。
  2. 再レビューと手直しの起動の仕方は、T5-2 に従う（Sprint 5 の振り返りで置き換えた）。
  3. extra-review は、次のどれかに当てはまる PBI だけ起動する。当てはまらない PBI は、ゴールデン値のテストの通過で代える。
     - 計算式・数値・乱数・CSV などの出力形式を変える。
     - 判定や順序（優先・時点）を変える。
     - ゴールデン値のファイルを変える。
- どうやって: 実行計画に、PBI ごとに「extra: 要／不要（理由）」を1行書く。再レビューの依頼には「再レビュー：範囲は must と差分だけ」と1行目に書く。
- 効果の確認: Sprint 5 で次の3つを満たせば効果ありとする。
  - 転記の誤りによる must と、それによる再判定が0回である。
  - 1pt あたりの tokens（振り返りを除く）が、Sprint 4 の 117,815 を下回る。
  - Sprint 5：転記の誤りは0回、1pt あたりの tokens は 105,589 で、この2つは満たした。再レビューの条件は満たさなかったので、項目2を T5-2 で置き換えた。Sprint 6 は、項目1・3と、1pt あたりの tokens が 105,589 を下回ることで判定する。
- 行き先: チーム合意

### T5-2: 手直しと再レビューは、元の Agent を再開せず、新しい Agent に必要な材料だけを渡して起動する（T4-3 の項目2を置き換える）
- なぜ（根本原因）: T4-3 は「再レビューに何を見せるか」（must と差分だけ）を決めたが、「どう起動するか」を決めていなかった。Sprint 5 では、SendMessage で元の Agent を再開した。再開した Agent は元の文脈をすべて読み直すので、範囲を絞っても tokens は下がらなかった。#7 の extra の再判定は 29,874 tokens で、初回の 26,526 より多かった。#7 のテストだけの手直しは 8 tool_uses で 96,875 tokens かかり、実装1件分に近かった。tokens を決めていたのは見せる範囲ではなく、持ち越した文脈の大きさだった（仮説。新しい Agent ではまだ測っていない）。
- 誰が: スクラムマスター（起動の仕方を選び、依頼を作る）
- いつ: レビューの後に、手直し（差し戻しを含む）か再レビューを依頼するとき
- どこで: 手直しと再レビューの依頼。スプリントファイルの「Agent 実行ログ」
- 何を:
  1. 手直しと再レビューは、SendMessage で再開しない。同じ枠の新しい Agent を起動する。手直しは isolation なしで、既存の作業ディレクトリで行わせる。
  2. 手直しの依頼には、指摘の原文、対象のファイルのパス、作業ディレクトリ、ブランチ、implement の報告の原文の場所だけを渡す。
  3. 再レビューの依頼には、前回の must の一覧、手直しの差分の範囲（`git diff <前回の承認対象>..HEAD`）、前回の判定を残したスプリントファイルの節の場所だけを渡す。レビュアーは、must の解消と手直しの差分だけを判定する。
- どうやって: 依頼の1行目に「手直し（または再レビュー）：範囲は指摘と差分だけ」と書く。実行ログの目的に「（新規起動）」と付け、同じ PBI の初回の tokens と並べて記録する。

### T5-3: 統合で競合を解消したら、解消の差分だけをレビューに通す
- なぜ（根本原因）: Sprint 5 の統合で、#7 と #23 が expr_evaluator.gd で競合した。implement は、clamp の lo > hi のエラーを #23 の形（名前と値を添える）に合わせて解消した。これは振る舞いを変える解消だったが、テストの通過だけで確かめ、どの枠のレビューも通さなかった。競合の解消を担当する枠も、レビューを通す条件も決まっていない。さらに、統合の解消をデモの作成と同じ起動で行ったので、解消の中身が記録から見えにくかった。#11 の code-review は merge-tree で競合を見込んだが、後から #23 が同じファイルを触ることは依頼に無く、見込みが外れた。
- 誰が: スクラムマスター（起動と依頼）。implement 枠（解消）。code-review 枠（解消の差分の判定）。extra-review 枠（計算・判定・ゴールデン値に触れる解消のとき）
- いつ: デモの準備で、統合ブランチに PBI のブランチを取り込んで競合したとき
- どこで: 統合の作業。スプリントファイルの「デモの準備」の記録
- 何を:
  1. 競合の解消は、デモの作成とは別の起動で implement に行わせる。
  2. 解消の報告には、競合したファイルごとに、両側の変更の要点と、どちらの振る舞いを残したかを書かせる。
  3. 解消のコミットの差分（`git diff <取り込み前>..<解消後>` のうち、競合したファイル）だけを code-review に渡して判定させる。計算式・判定・ゴールデン値に触れるときは、extra-review にも渡す。
  4. 判定が approve になってから、デモの作成を起動する。
- どうやって: 依頼の1行目に「統合の競合の解消のレビュー：範囲は競合したファイルの解消の差分だけ」と書く。判定はスプリントファイルの「デモの準備」に残す。
- 効果の確認: Sprint 6 で、競合を解消した統合のすべてに、解消のレビューの判定が付いていれば効果ありとする。競合が無ければ「判定不能」とする。
- 行き先: チーム合意

### T6-2: 測定は再現の条件を決めて残し、上限や検査を足す PBI は既存のモデルとデモへの影響を計画で確かめる
- なぜ（根本原因）: Sprint 6 で、#37 の測定のモデル（条件990個×761文字）が、同じスプリントの #45 の上限（10万命令）で作れなくなった。デモの場面1は「変更前は報告の値、変更後は別の形」の注記つきの比較になった。変更前の値は、その時の環境で1回測った数字として報告に書かれ、変更前のコミットで同じ入力を再実行できる形ではなかった（1000文字の変更前は2ターンだけで 5741〜9256 ms と幅が大きかった）。測定の再現の条件（基準のコミット、入力の作り方、反復の回数と統計量）が決まっていない。上限や検査を足す PBI が、既存のモデル・テスト・デモ・測定を壊さないかを確かめる場面も、計画にも実装の報告にも無い。
- 誰が: スクラムマスター（計画）。implement 枠（測定と影響の報告）。extra-review 枠（比較の方法を確かめる）
- いつ: スプリント計画で PBI の順序を決めるとき。測定を伴う PBI と、上限・検査を足す PBI の実装の報告のとき
- どこで: スプリント計画の実行計画。実装の報告の「列7の規模と実測」の節と assumptions
- 何を:
  1. 測定を伴う報告には、次の4点を書く。
     - 基準のコミットのハッシュ（変更前の値を測ったコミット）
     - 入力を作るスクリプトの場所と引数
     - 反復は3回以上とし、中央値と範囲を書く
     - 変更の前後は、同じ入力・同じ環境で測り、比で示す
  2. 上限や検査を足す PBI の報告には、assumptions に「既存のモデルへの影響」を書く。既存のテスト・サンプル・デモ・測定用のモデルを新しい上限で読み込み、通らないものを列挙する。
  3. スクラムマスターは、計画で「測定を伴う PBI」と「上限・検査を足す PBI」の組を実行計画に表で書く。組があれば、測定を上限の前のブランチで先に録るか、測定用に上限を外せる形にするかを決め、デモの台本に反映する。
- どうやって: 実装の依頼の共通ファイルに、1の4点と2の1行を書く。実行計画に「測定 × 上限」の表の欄を設ける。
- 効果の確認: Sprint 7 で、次を満たせば効果ありとする。該当する PBI が無ければ「判定不能」とする。
  - 測定を伴う報告のすべてに4点がそろっている。
  - 上限や検査を足したことが原因の、デモの台本の作り直しと、他の PBI の前提の破れが0件である。
- 行き先: チーム合意
