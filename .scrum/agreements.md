# チーム合意

### T1-1: 外部入力と数値の受け入れ方針を守る
- なぜ（根本原因）: 他の制作者が書いたモデルから来る値を、どこまで受け入れるかの方針が一箇所に書かれていない。そのため、実装者は PBI ごとに暗黙の仮定を置く。NaN・無限大、巨大な数値リテラル、空の名前、上限が無いことを、レビューで初めて見つけることになり、スプリント1では3つの枠が重ねて指摘した。
- 誰が: implement 枠（実装時）、code-review 枠・security-review 枠・extra-review 枠（判定時）
- いつ: モデルの定義・式・読み込みなど、外部由来の値を受け取るコードを書く、またはレビューするとき
- どこで: src/ の定義関数・パーサ・評価器と、そのテスト
- 何を: 次の方針に従う。方針から外れる実装は、理由を報告の assumptions に書く。
  1. 数値は有限でなければならない。NaN・無限大は、定義時またはパース時に、位置つきのエラーで拒否する。非有限になる数値リテラルも同じく拒否する。
  2. 失敗を NAN などの値で返さない。失敗は `Error` コードと `last_error` で返し、`last_error` は成功したときに空にする。
  3. 名前は空にできない。名前の長さ、定義の個数、式の長さと入れ子の深さには、上限を置く。
  4. 利用者の入力をログやエラー文に出すときは、制御文字（改行・タブ・bidi 制御・ゼロ幅文字など）をエスケープする。
- どうやって:
  - implement は、上の1〜4について、それぞれを破る入力のテストを1件以上書く。
  - レビュアーは、1〜4に反する実装を must とする。
- 効果の確認: スプリント2のレビューで、1〜4に当たる指摘が should も含めて0件であり、同じ種類の指摘を2つ以上の枠が重ねていなければ、効果ありとする。
- 行き先: チーム合意

### T1-2: should の指摘に行き先を付け、重なったものを後続 PBI に流す
- なぜ（根本原因）: should はマージを止めないので、誰も引き取らない。また、判定書式にも記録にも、行き先を書く場所が無い。スプリント1では34件の should が行き先を持たずに残り、同じ種類の指摘が PBI をまたいで繰り返された。
- 誰が: code-review 枠・security-review 枠・extra-review 枠（指摘時）、スクラムマスター（集約時）
- いつ: 各 PBI のレビューで should を出すとき。および、スプリントの実行フェーズを終えて `phase` を `demo` にする直前
- どこで: レビューの findings、スプリントファイルの「記録」、バックログの PBI のコメント
- 何を:
  - レビュアーは、should の各行の末尾に「→ 行き先」を1つ書く。行き先は `#<PBI番号> の受け入れ基準`、`新規改善 PBI`、`対応不要（理由）` のどれかとする。
  - スクラムマスターは、should を集約表（指摘・枠・行き先）にまとめる。
- どうやって:
  - スクラムマスターは、レビューの依頼に「should には → 行き先を付ける」と書く。
  - 次の2種類の should は、スクラムマスターが行き先の PBI に、受け入れ基準の追記案としてコメントする（`retro` ではなく `review: Sprint <N>` と書く）。
    - 2つ以上の枠が重ねて出したもの
    - security-review が出したもの
  - 追記するかどうかは、次のリファインメントで PO が決める。
- 効果の確認: スプリント2の記録で、行き先が書かれた should が90%以上あり、重なった should がすべて PBI にコメントされていれば、効果ありとする。
- 行き先: チーム合意
